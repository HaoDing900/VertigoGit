存档菜单的显示文字 · 地点与调查阶段

存档里存的是 key（地图名、stage 名），玩家看到的文字在画的时候才从表里查。 所以改文案、补翻译对老存档一样生效，而且内部名字永远不会漏给玩家。

加一条新的

  1. 打开对应的表，Add 一行
  2. 行名填内部名字（地图短名或 stage 名，照抄，不要改）
  3. Display Text 填玩家看的文字
  4. 按本地化流程补译文（见下）

不需要改 C++。

本地化

Display 是有稳定身份的 FText，命名空间固定为 VTG.SaveDisplay， key 就是行名。走项目现有那套手工多语言面板，和别的 UI 文字完全一样：

  1. 切到 Origin，填好原文，保存资产
  2. 在文本下方的「多语言译文」折叠区填英文、中文
  3. 勾上「确认是玩家可见文本」（不勾的话编译会跳过这一条，译文框也是禁用的）
  4. 点「保存并应用译文」

现有 31 行都已收集进 Localization/ManualTranslations.json、都勾了确认、 en-US 与 zh-Hans 的译文都已填好，三份 locres 已重新编译。 改文案时记得译文的 reviewedSource 会和新原文不一致 —— 面板会标成"待复核"，不会编译旧译文。

保存译文源表和编译游戏资源是两步。 只离开输入框不代表游戏已经用上新译文。

二、维护

工具

命令做什么
-run=VTGSaveDisplayNames只验证：断言 31 行逐行解析正确、行数对得上、每行都带文本身份
-run=VTGSaveDisplayNames -Apply建表 / 补缺行 / 写 settings / 收集进翻译表 / 勾确认 / 填中英译文 / 编译 locres
-run=VTGSaveDisplayNames -Apply -Reseed额外：把已有行改回 C++ 里那份基线（会盖掉编辑器里改过的字）

-Apply 不会覆盖已经写好的文字，只补缺的行，所以重跑安全。 唯一的例外是「这一行没有文本身份」—— 那种会被就地补上身份，文字原样保留。 -Reseed 是那个会覆盖的开关，只在"以代码里那张表为准"时用。

行数据在哪

VTGSaveDisplayNamesCommandlet.cpp 的 Locations[] / Phases[]， 一行三列：行名、英文、中文。译文经 VTGManualLocalization::SetTranslation 写入翻译表 —— 和面板保存走同一套格式校验，同样把 reviewedSource 记成当时的原文。

日常加地点 / 阶段不用跑这个工具，也不用改 C++。 在对应表里加一行，行名抄内部名字， 文字自己写，然后走面板填译文就行。只有想把整张表当代码基线固定下来时才动 C++。

日常维护要点

  • 地图或 stage 改名了，表里的行名要跟着改，否则那一行查不到：地点退回原始样式，阶段整行消失。
  • 新加的行默认没勾确认（面板收集进来的都是未确认）。不勾就编译不进去。
  • 改了原文就要重填译文：译文带着"复核过的原文"快照，原文一变，旧译文不再编译。

三、原理

解析在哪

UVTGSaveDisplayNames::ResolveLocation(LevelName)   // 地点，查不到则回退
UVTGSaveDisplayNames::ResolvePhase(Stage)          // 阶段，查不到则返回空

由 UVTGTerminalSavePage 在画列表行和详情页时调用。主菜单的 Continue 用的是同一个页面， 所以改一处两处生效。

为什么不把文字存进存档

存档里继续只存 Meta.LevelName 和 Meta.Stage。如果把显示文字烤进存档：

  • 以后改文案或补翻译，老存档看不到
  • 存的时候是什么语言，读出来就还是什么语言（中文会话里蹦英文）

DisplayLabel 就是这个毛病的实例：它是存档时 FString::Printf(TEXT("Manual Save %02d")) 烤进去的英文，渲染时又套了 AsCultureInvariant，所以永远不会翻译。详情页那一行已经删掉 —— 它和正上方的标题 MANUAL SAVE {Slot} 是同一个东西，而标题本来就是 NSLOCTEXT，能翻译。

DisplayLabel 字段本身保留在存档结构里，以后做「玩家自己给存档命名」还用得上。 那种是用户内容，存字符串、不本地化，是对的。

为什么能用 DataTable

一度担心 DataTable 的行数据不是反射属性、面板收集不到。实际上已经特判过了：

// VTGManualLocalization.cpp，GatherAsset
// DataTable rows are raw struct memory, not reflected UObject properties.
if(auto* Table=Cast<UDataTable>(Object))if(Table->GetRowStruct())
    for(const auto& Row:Table->GetRowMap())for(TFieldIterator<FProperty> It(Table->GetRowStruct());It;++It)
        ...
但 FText::AsCultureInvariant 建出来的文字收集不到。 同一个 gather 里有一行 if(... || Text.IsCultureInvariant() || ...)return; —— 文化无关的文字被直接跳过。 第一版种子行就是这么建的，等于做了一张永远翻不了的表。现在种子用 FText::ChangeKey(TEXT("VTG.SaveDisplay"), 行名, ...)，并且工具里有断言守着每行都带身份。

第三道门：字段白名单

折叠译文区不是所有 FText 都有。VTGAssetDisplayLocalizationDetails::IsDisplayField 是一张 (Owner, Name) 白名单，不在里面的 FText 在 Details 面板里就只是个普通输入框 —— 文字能写、能存，但没有翻译入口。FVTGSaveDisplayRow::Display 已经加进去了。

顺带把定位行来源的 GetDataTableRowContext（原 GetMailContext）放宽了： 它原来写死只认 Mail 的行结构，现在对任何结构体拥有的白名单字段都生效，所以以后再加表不用改它。

确认勾选做什么

approvedDisplayText 不只是个标记：

  • 编译时 if(!E->Approved || !E->LockReason.IsEmpty())continue; —— 没勾的条目直接跳过
  • 面板里译文输入框的 IsEnabled 也看它 —— 没勾就填不了

所以「收集到了」不等于「能翻译了」。这六条在工具里一并勾上了，因为它们存在的唯一目的就是给玩家看。
