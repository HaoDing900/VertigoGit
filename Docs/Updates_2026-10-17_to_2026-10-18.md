## 4. Narrative → Mail → Note 的输入与动画生命周期

### 输入归属

- Narrative 和 Note 分别持有自己的输入请求；Note 优先级更高。结束 Dialogue 只释放 Dialogue 自己的请求，不会放开仍打开的 Note。
- `UNarrativeUIInputComponent` 统一维护 UI 输入、鼠标和移动／视角锁，只平衡自身增加的 ignore-input 计数。
- `PC_Game_VTG` 使用 `AVTGPlayerController` 作为父类，阻止旧蓝图延迟的 GameOnly / GameAndUI 调用覆盖仍有效的模态输入。
- `WB_NoteMainWidget` 使用 `UVTGNoteInputWidget`，在逻辑 Closed 时释放请求；关闭动画／缓存根控件不再导致输入一直停在 UI。销毁提供兜底。
- 修复 Sewer 的 Note 完成事件：从孤立 Custom Event 恢复为父 BPLM 的真正 override ` OnStoryNoteFinished`（名称原本带前导空格），让 Police / Overdue 的关 Note 后剧情继续执行。

### 保持读信动作直到关 Note

- `On Finish Reading Mail` 保留为统一入口；原有状态、终端动画、镜头和输入清理集中到 `FinishMailReadingCleanup`。
- `OpenStoryNote` 在结束 Dialogue 前先登记 hold，覆盖 Note 创建前的空档。Note 关闭后，延后的清理只执行一次；普通邮件仍立即执行。
- BPLM → `Mail | Story Note` → **Keep Mail Reading During Story Note** 默认开启，可关闭以恢复原结束时机。

说明：[NoteInputOwnership.md](NoteInputOwnership.md)、[MailStoryFlow.md](MailStoryFlow.md)。备份：`Saved/Backups/NoteInputOwnership/`、`Saved/Backups/MailStoryFlow/`。

## 7. 本次新增：楼梯 Lock Cam 越来越靠近 Sa

排查对象：`L3_SaSitOnStairs → LockCameraByID(L3StairSaSit1)`。

**原因已复现**：Lock Point 本身是普通 CameraActor，没有弹簧臂，也没有移动它的 Tick。关 Note 后，终端清理先等待 0.2 + 0.8 秒，然后用 1 秒 Blend 重新设置 View Target；这时剧情已经锁定楼梯镜头，旧清理却把画面切回玩家跟随相机或之前 Activated 的固定相机。看到的“靠近”来自视角被换走，Lock Point 的 Transform 本身未移动。这是读信清理延后后暴露出的镜头归属冲突。

**本次修复**：`BP_Player_Sa` 的镜头返回分支增加 `Can Restore Mail View Target` 判断。只有当前 View Target 仍是读信玩家时，旧清理才允许恢复原视角；如果后续的 Lock Cam／Narrative 已接管，就跳过这次 View Target 修改，同时继续关闭 MailCamera、恢复跟随相机组件、隐藏终端并清理邮件状态。

- Runtime：`VTGMailReadingComponent.h/.cpp` 的 `CanRestoreMailViewTarget`。
- Blueprint：`BP_Player_Sa.EventGraph` → `VTG_MailCameraStillOwned` 分支。
- 备份：`Saved/Backups/MailCameraOwnership/BP_Player_Sa-before-view-target-guard.uasset`。
- 验证工具：`-run=VTGMailFlow -VerifyMailCamera`。
- 已在实际蓝图的相机返回分支复现旧故障：View Target 被抢走，但 Lock Point Transform 不变。修复后楼梯视角保留，邮件状态仍清理；旧 Activated 相机不能抢回画面，普通邮件仍能正常回到固定相机。完整关卡中的构图和视觉衔接仍需人工检查。
- 编译、保存后独立进程回读及镜头运行验证通过；`mail-camera-final-tests.log` 中 7 项事件时机／邮件／Note／输入／跳转回归全部通过。
